# viewer 主基线：WiFi 常开空闲直读与开网页录屏（2026-11-10 21:02–21:25）

**结论：主基线 viewer（WiFi 常开 + 每小时一张）稳定后，USB 表直读 `0.09 A / 5.04 V / 0.45 W`；同一轮上电的录屏里，打开网页后电流抬到 `0.11–0.14 A`。这是本项目对 viewer 常开空闲（P6）的第一次直接读数，此前只有省电版窗口段的 95 mA 作代理值。**

## 现场

- 固件：`esp32cam-viewer`（主基线，WiFi 常开 + 网页 + 每小时一张），2026-11-10 晚间构建（`.arduino/build-viewer` 20:10）后烧录。**判定依据**：电流持续 `0.09 A`——省电版在 15 min 窗口关闭后读 `0.00 A`，只有 viewer 会把 WiFi 一直挂着
- 供电：充电宝 → USB 电压电流表 → ESP32-CAM 5V/GND；量的是表后整条路径（含 AMS1117、摄像头、SD），与 19:40 那轮口径相同
- 时间：照片水印 2026-11-10 21:02（星期二）；表上计时 `0:08`，即该次上电约 20:54（读数已稳定）
- 表上读数（见 `frame_meter_zoom.jpg` 特写）：`5.04 V` / `0.09 A` / `0.45 W` / 累计 `64 mWh` / 计时 `0:08`
- 录屏：`video_20261110_212524772.mp4`（21:25，49.4 s / 720×1280 / 无音轨）；表上计时 `0:31`，与 21:02 的 `0:08` 对得上，是同一轮上电（约 20:54）

## 自洽性核对

| 核对项 | 算法 | 结果 |
|---|---|---|
| A 与 W 是否一致 | `0.09 A × 5.04 V` | `0.454 W` ≈ 表显 `0.45 W`，这一刻两个字段自洽（不像 19:40 那轮 W 字段滞后一档） |
| 瞬时值与累计值是否一致 | `64 mWh ÷ 8 min` | `0.48 W` → 平均 `≈ 0.095 A`，与瞬时 `0.09 A` 差 1 个字，说明这 8 min 电流一直停在这一档 |
| 量化误差 | 0.01 A 分辨率 | 读数 `0.09 A` 对应 `90 ± 5 mA`（±5 %） |

## 能得出什么

- viewer 常开空闲 ≈ `90 mA`（`0.09 A`），与省电版窗口空闲段 `0.09–0.10 A`（另一轮独立测量）在 1 个字内一致：**两条固件「开着 WiFi 什么都不干」的底值相同**，跨固件对比可以成立。
- 与固件里的模型 `kModelIdleMa = 45 mA` 比，实测是它的 **2 倍**；差值主要来自模型不含 WiFi 电流（`esp32cam-viewer/README.md` 已注明该模型只记 45 mA）。
- 因此 `baseline-24h-2026-11-09` 的 `POWER.CSV`（全部按 `45 mA` 记账、电压 `v5_mv = -1`）对 viewer 是**低估值**；按 `90 mA` 常开外推约 `2.16 Ah/天`，模型口径约 `1.08 Ah/天`，量级差 2 倍。这只是外推，不是 24 h 实测。

## 不能得出什么

- **不是 24 h 连续记录**：单个时刻 + 8 min 累计，覆盖不到每小时一次的拍照；拍照瞬时在这块 0.01 A 表上仍不可分辨（见 [powersave-meter-2026-11-10](../powersave-meter-2026-11-10/README.md)）。
- **电压口径不可直接混用**：本轮 `5.04 V`，19:40 那轮 `4.90 V`，差的 3 % 来自表/线自身的压降不同，不是板子变了。`mAh` 与平均电流结论不受电压影响，只有换算 `Wh` 时要按当轮电压。
- **单次读数不等于统计结论**：要证伪 `45 mA` 模型，得连续对齐 `POWER.CSV` 与表读数，而不是拍一张照片。
- 照片只能证明「这一时刻表上显示 0.09 A」，不能证明 8 min 里没有低电流间隙——间隙由累计量反推排除到 ±1 个字。

## 开网页时：0.09 → 0.11–0.14 A（21:25 录屏）

同一轮上电里，在浏览器打开 viewer 自己的网页、翻图时录了 49 s：

| 时刻 | 电压 | 电流 | W 字段 | 备注 |
|---|---|---|---|---|
| t≈2 s（未开网页） | `5.04 V` | `0.09 A` | `2.30 W`（残留） | 停在之前的瞬态（≈0.46 A），**不能当电流用** |
| t≈8–44 s（开着网页翻图） | `5.04 V` | `0.11–0.14 A`，典型 `0.13–0.14 A` | `0.55 W`（≈0.11 A，滞后一档） | 中间偶有 `0.04–0.05 A` 的低帧 |
| t≈44 s（末帧） | `5.04 V` | `0.10 A` | `0.50 W` | 回到空闲档 |

- 与省电版窗口段「刷页面 `0.12–0.19 A`」量级一致；viewer 这轮 WiFi 一直开着，只是打开自己的网页，所以抬升幅度比省电版小。
- **W 字段仍不可用**：`2.30 W` / `0.55 W` 都与 `A × V` 对不上，与 [powersave-meter README](../powersave-meter-2026-11-10/README.md) 记的「W 更新比 A 慢」一致；功率与能量统一用 `A × V` 或累计 mWh 算。
- 49 s 里累计只涨 `4 mWh`（`243 → 247`），量化太粗，不能用它反推这段的平均电流。

## 复现（裁出表盘特写）

```bash
ffmpeg -v error -y -i IMG_20261110_210230081.jpg \
  -vf "crop=620:700:1210:2090,scale=1240:-1:flags=lanczos" frame_meter_zoom.jpg
```

画面偏暗是手机室内拍照，不影响读数；表盘数字在原图里 7 段码清晰可读。

录屏的抽帧：

```bash
# 表盘特写（t≈20 s，转 90° 把数字正过来）
ffmpeg -ss 20 -i video_20261110_212524772.mp4 -frames:v 1 \
  -vf "crop=220:300:390:830,transpose=2,scale=1200:-1:flags=lanczos" frame_web_load_zoom.jpg

# 每 4 s 一帧、共 12 帧的拼图（核对电流爬升；不归档，写 /tmp 就行）
ffmpeg -i video_20261110_212524772.mp4 \
  -vf "fps=1/4,crop=220:280:390:840,scale=300:-1,tile=4x3" -frames:v 1 /tmp/montage.jpg
```

本机 `ffmpeg` 的解码器是 openSUSE 的 `libopenh264-8 ~noopenh264` 桩库，直接抽帧会报 `Unable to create decoder`；要么按 [powersave-meter README](../powersave-meter-2026-11-10/README.md) 用 Cisco 官方库（`LD_LIBRARY_PATH` 指过去），要么装 Packman 源的 ffmpeg。
